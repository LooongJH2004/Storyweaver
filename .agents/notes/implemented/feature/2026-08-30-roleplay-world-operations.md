# Agent Note: Roleplaying world operations and portable stories

Status: implemented

English | [中文](2026-08-30-roleplay-world-operations.zh.md)

## Problem

Storyweaver already had durable Stories, isolated Actor Sessions, a Plot Ledger, and exact-revision Director runs, but the roleplaying loop still stopped at durable intent. Player authority was mostly represented by editable prompt markers; Actor speech and action had no typed world-outcome settlement or audience delivery. Long-story memory and multi-Actor discussion lacked durable review and floor state. Context inspection could describe sections but could not safely edit their order or budget. Storybook export was not enough to move a complete Story with its Sessions and world files.

The earlier AIAgentRolePlay MVP demonstrated useful player-facing surfaces for state, memory, discussion, observation, interruption, and perspective. Its page-local state, arbitrary deep updates, destructive rerolls, and in-memory watchdogs could not become authoritative Storyweaver behavior because they bypass provenance, revisions, information boundaries, and recovery.

## Decision

The version-5 Story aggregate owns revisioned world, memory, discussion, context-recipe records, and Story-local prompt overrides. World changes use strict `set` and `remove` path operations over JSON values. Unsafe prototype path segments are rejected. A sourced Actor event can be accepted or rejected exactly once; accepted settlement records typed facts, applies its patch, and writes separate perception deliveries for the declared audience. Actors receive only their own deliveries. Trusted PlayerAuthority exposes separate choose-direction, intervene-world, speak-as, and act-as commands with player provenance instead of overloading ordinary chat.

Long-story memory is a proposal and review workflow. Pending or rejected entries never enter model context. Approval can supersede an older approved entry of the same kind, preserving audit history while exposing only the active version. Durable discussion records initiation provenance, participants, current speaker, queue, transcript, round count, maximum rounds, summarizing, completion, and player intervention. The storybook owns the player-authored maximum for automatically started discussions, with a materialized baseline of 4 rounds when the field is absent; an explicit saved value is never migrated implicitly. Each discussion snapshots the current value when it starts, while the advanced player operation may choose a per-discussion value directly. The Director starts discussions from plot needs and chooses participants and opening order, but cannot replace the player's automatic round limit. One Host dispatch advances accepted Actor speech along the durable floor until explicit intervention, Actor failure, an Actor-owned conclusion, or the round budget. It derives used and remaining speaking opportunities plus opening, developing, closing, or summarizing phase from participant count and durable turns, and supplies that progress to the Director and participating Actor. Actors advance their own goals and stakes instead of serving a hidden expected plot answer; the closing phase asks them to make a concrete choice, bargain, consequential refusal, or character-owned conclusion. When a floor returns to an Actor already completed in the current Director Run, the Host requeues only that exact floor owner over the current Run revision, retains prior accepted event references, and mints a fresh attempt; ordinary completed Actors remain non-retryable. A player may request a speaking turn, ask the Director to converge, resume after that request is resolved, or interrupt. While a speaking or convergence request is pending—even if the current Actor call is still settling—the player may cancel it; exact-revision clearing removes the intervention marker and returns the durable discussion to automatic `active` dispatch. Natural or budgeted conclusion enters a durable summarizing state; an independently bounded Host continuation supplies exact revisions and requires the Director to narrate concrete agreements, unresolved disagreements, and the immediate transition before completion. That summary and successful closure complete the current observe-and-advance request without a separate Brief or post-discussion beat, as refined by [Director opening tool scheduling](../bug-fix/2026-09-03-director-opening-tool-scheduling.md). Manual creation and floor editing remain advanced interventions rather than the normal startup path.

The canonical storybook owns one reusable Director prompt and one private role prompt per Actor. New runs copy those baselines with authored storybook material. The Story aggregate stores exact-revision overrides, so changing one run cannot mutate another. Read and update Remotes report the baseline, override, effective value, and source; clearing an override restores the storybook value. The Director receives only its effective custom prompt after locked product policy, and each Actor receives only its own effective role prompt. Export, import, and reload preserve both layers.

The context recipe is a complete, exact-revision list for Director and Actor audiences. Players may enable, reorder, and set character budgets for creative sections. Product policy, tool protocol, and Actor identity are locked and cannot be disabled. Model composition and browser preview apply the same recipe and report full characters, included characters, and estimated tokens. Actor composition filters world perceptions, memory notes, and discussions by Actor identity.

Story Controller exposes these operations as path-free typed Remotes and projects runtime state in `StoryView`, while prompt values use an explicit read/update boundary to avoid broad private-context projection. Director tools can settle one sourced event, propose memory, and automatically start or resolve a discussion without receiving player review authority. The roleplaying Client provides a dedicated prompt workspace and a responsive, status-first World Operations workspace; lower-level forms remain available through progressive disclosure. The Story library exposes a persistent import action that accepts either a standalone version-4 Storybook as a newly validated authored-settings template or a complete Story Package as a fresh aggregate.

A strict version-1 Story Package contains the Story record including prompt overrides, canonical storybook including prompt baselines, every registered Session log, and bounded portable files below `world/`. Export fails if a registered Session is unavailable, avoiding a silently partial package. Import validates size limits, paths, role invariants, and every Session log before mutation, then mints a fresh Story identity and fresh Session identities and rewrites all internal ownership references. It never overwrites an existing aggregate or restores imported opaque ids.

## Alternatives considered

**Reuse arbitrary nested state merges from the MVP.** This was flexible but could mutate reserved object paths, erase unrelated state, and provide no exact-revision conflict boundary. Typed path operations make every mutation inspectable and reject unsafe segments.

**Treat accepted Actor intent as an automatic outcome.** This would collapse character intent, world truth, and audience knowledge into one event. Explicit settlement preserves the distinction and lets rejection remain durable evidence.

**Let the model write long-term memory directly.** Model-authored memory would become self-validating context and could silently rewrite continuity. Proposal plus player review keeps persistence useful without granting canonicalization authority.

**Run discussions with an in-memory loop or watchdog.** A process restart would lose floor ownership and round progress. Story-owned discussion state makes resume and player intervention deterministic.

**Let the Director choose a fixed or model-authored automatic discussion limit.** A fixed limit cannot fit both short exchanges and large ensembles, while a model-authored limit makes a player preference advisory. The storybook value is player-owned and inherited by new runs; the model may conclude early but cannot enlarge the budget.

**Expose a generic context JSON patcher.** It could disable safety policy or leak Director-only material to Actors. A closed section vocabulary and locked mandatory sections preserve the information boundary.

**Export only Storybook JSON or preserve imported ids.** Storybook-only export loses runtime continuity; preserving ids risks collisions and accidental ownership of existing Sessions. The package is complete within explicit limits and always imports as a new aggregate.

## Consequences

Storyweaver now closes the P0 roleplaying loop from typed intent through explicit world outcome and audience-specific perception. It also supplies the P1 continuity surfaces needed for longer play: reusable and run-local prompt authoring, reviewed superseding memory, player-bounded automatically orchestrated and resumable group discussion, safe context budgeting, and complete portable Story exchange. Discussion progress is derived rather than stored twice, so a restart preserves the inputs and recomputes the same phase. Automatic continuation can spend multiple Actor calls in one player turn, but the durable player-authored round budget remains the hard bound. The Client borrows the useful operational categories and persistent live-discussion emphasis of the MVP while keeping Host state authoritative and making intervention secondary to visible automatic state.

Settlement is intentionally not inferred from prose, memory approval remains a trusted player action, and imported packages always create new identities. Narrative clocks still have no independent scheduler, semantic memory compaction is not automatic, and richer asset-specific behavior remains future work.
