> 文档级别：最高优先级项目交接说明；适用项目：`D:\projects\dsh-roleplay`；参考项目：`D:\projects\AIAgentRolePlay`；最近整理：2026-09-03

> 2026-09-12 专项入口：[群组讨论、感知与记忆优化计划](../.agents/notes/implemented/feature/2026-09-12-discussion-perception-memory.zh.md)。文档整理后继续执行完整实现目标，保留工作区已有实现和评测记录。该计划以当前独立版源码及既有未提交改动为基线；本文旧 Story/Brief 运行描述保留为历史参照，不覆盖独立版链路。修改前同时读取[功能清单中的专项范围](roleplay-feature-status.zh.md#群组讨论感知与记忆专项)与计划中的回归保护边界。

## 1. 这份文档解决什么问题

`dsh-roleplay` 是当前继续开发的项目，来源于 DeepSeek Harness，但产品目标已经转向 Storyweaver 角色扮演应用。`AIAgentRolePlay` 是先前可运行的 MVP，其中包含已经验证过的产品语义、交互方式和前后端协作流程。后续开发必须同时理解两个项目，不能只根据 `dsh-roleplay` 当前局部代码推断产品需求。

本轮开发暴露出的主要问题不是单个 Bug，而是调研和实现顺序错误：没有先完整梳理 MVP 已有功能和当前项目的端到端链路，就开始大范围增加 P0/P1 能力；之后又把“存在领域字段”“存在 API”或“存在一个操作面板”误写成完整功能，造成既有能力被遗漏、弱化或难以发现。

这份文档用于给后续 Agent 建立统一起点。它记录产品目标、历史功能证据、不可随意改变的行为、当前文档可信度和开发方法。具体代码仍是实现证据，但任何局部代码都不能单独证明功能完整。

## 2. 事实等级

阅读项目资料时必须区分以下四种事实，不得混写。

| 等级 | 含义 |
|---|---|
| 用户确认的产品语义 | 用户在开发过程中明确要求的行为，是最高优先级产品依据。 |
| MVP 历史证据 | `AIAgentRolePlay` 中存在可追踪的前端、后端、持久化或运行时链路，说明该能力不是凭空新增。 |
| 当前源码证据 | `dsh-roleplay` 当前工作区存在对应代码，但只有完整贯通后才能称为可用功能。 |
| 未核验 | 只看到名称、类型、测试夹具、文案或某一层实现，不能判断功能是否可用。 |

[角色扮演功能现状清单](roleplay-feature-status.zh.md)最初主要依据当前源码整理，遗漏了部分 MVP 历史能力。它可以作为检索索引，但在完成跨项目、跨层核对前，不能单独作为“已实现”结论。

## 3. 原始任务与产品方向

最初任务包含两个相互关联的目标。

1. 从 `AIAgentRolePlay` 中识别值得迁移到 `dsh-roleplay` 的角色扮演功能。
2. 继续裁剪 DeepSeek Harness 中与角色扮演产品无关的能力。

这两个目标都要求先做完整对照。迁移功能时要保留 MVP 已验证的产品语义，再利用 Harness 的插件、Session、工具、持久化和模型编排能力重构实现。裁剪 Harness 时必须证明目标能力不被 Storyweaver 使用，不能仅因为当前 UI 没有入口就删除底层能力。

当前产品不是通用编程 Agent，也不是把 Harness 控制台换一套配色。它是以故事书、独立故事运行、导演编排、自主角色、世界状态和玩家干预为核心的角色扮演应用。

## 4. MVP 中必须优先核对的已有能力

### 4.1 导演与角色提示词编辑

`AIAgentRolePlay` 已经存在导演提示词和角色设定的编辑、保存与上下文渲染链路，不能把它们当成后续才想到的新功能。

- `AgentAIRolePlay_V2/frontend/src/views/EditorView.vue` 提供故事编辑入口。
- `AgentAIRolePlay_V2/frontend/src/components/editor/forms/WorldSettingsForm.vue` 编辑 `director_prompt`。
- `AgentAIRolePlay_V2/frontend/src/components/editor/forms/CharacterSettingsForm.vue` 编辑指定角色的 `identity_prompt`。
- `AgentAIRolePlay_V2/backend/app/schemas/models.py` 持有角色提示词字段。
- `AgentAIRolePlay_V2/backend/app/core/context_engine/template_renderer.py` 把导演和角色提示词写入各自模型上下文。
- `AgentAIRolePlay_V2/backend/app/api/routers/story.py` 与存储模块负责角色和故事配置的读写。

Storyweaver 中的对应功能必须覆盖编辑入口、目标选择、保存、重新加载、故事书基础值、单次故事覆盖值以及实际模型注入。缺少其中任意一层，都不能称为“支持提示词编辑”。系统强制规则可以保持锁定，但不能因此取消玩家可编辑的导演设定和角色设定。

### 4.2 自动群组讨论

`AIAgentRolePlay` 的群组讨论不是单纯的玩家手工表单。NPC 可以提出讨论请求，运行时保存请求和讨论状态，讨论管理器自动选择发言者并推进轮次，玩家可以允许、拒绝、插话或打断，最终再交回导演裁定。

- `AgentAIRolePlay_V2/backend/app/interaction/chat/message_persister.py` 保存 `pending_discussion_request`。
- `AgentAIRolePlay_V2/backend/app/interaction/discussion_manager.py` 管理讨论状态、发言顺序、超时、玩家插话和导演收束。
- `AgentAIRolePlay_V2/backend/app/interaction/chat/sse_broadcaster.py` 向前端发布讨论请求和状态。
- `AgentAIRolePlay_V2/frontend/src/components/play/DiscussionWidget.vue` 展示自动触发的讨论请求和进行状态。
- `AgentAIRolePlay_V2/frontend/src/views/play/ChatInputBox.vue` 在讨论中提供玩家插话能力。

Storyweaver 可以优化这套机制，但默认运行方式仍应是模型与运行时按剧情触发和推进，玩家界面负责观察、回应和干预。手工创建讨论可以作为高级操作，不能成为讨论功能工作的必要前提。

### 4.3 故事编辑与角色配置

MVP 的编辑器不仅编辑文本，还组织世界设定、角色、模型参数和上下文管线。迁移时应先确认每一项能力的产品用途，再决定保留、合并或舍弃。不能因为新项目采用不同领域模型，就把旧编辑器承载的用户能力一并丢失。

## 5. 用户已经确认的 Storyweaver 行为

### 5.1 故事书与独立故事

- 故事书保存基础世界和角色设定。
- 故事书旁的加号基于基础设定从头创建一个独立故事，不继承其他故事窗口的运行历史。
- 同一故事书可以拥有多次互不污染的故事运行。
- 删除一次故事表示删除该次运行，不等于删除故事书。
- 删除故事书下最后一次运行后，故事书仍然显示，并允许再次从基础设定开始。

### 5.2 撤回重发

- 消息上的小铅笔属于同一 Session 内的撤回重发。
- 它不能创建新分支，也不能创建新的故事或 Session。
- 新内容替换目标消息及其后的旧表层历史；旧事件继续保留在追加式日志中，其中旧人工输入与 AI 回答作为 replacement 气泡下方的折叠版本历史供查看，但不进入当前 transcript 顺序、导航或模型上下文。
- Storyweaver 在玩家回合前保存 Story 与 Actor 检查点。重编会恢复仍在保留窗口内的准确检查点；首个旧回合可回到确定的空基线，其他缺少检查点的回合必须明确拒绝，不能从当前状态继续生成。

### 5.3 导演大纲

- 新故事的初始导演大纲为空。
- 首次推进时，导演应优先自动创建大纲初稿。
- 大纲为空时不能直接提交依赖大纲的单轮 Brief。
- 《月影账簿》的 `director-outline.json` 只用于结构参考，不应作为新故事的预填运行数据。

### 5.4 提示词与角色设定

- 玩家必须能够编辑导演设定。
- 玩家必须能够选择具体角色并编辑该角色设定。
- 叙事主角可不指定，角色列表非空时也允许 null；指定时必须引用已有角色。该标记不决定玩家控制权，玩家仍可代演任意角色。
- 编辑结果必须持久化并进入对应模型的下一次有效上下文。
- 一个角色的私有设定不能泄露给其他角色。

### 5.5 群组讨论

- 群组讨论默认由剧情和角色行为自动触发并推进。
- 玩家可以观察讨论状态，并在需要时允许、拒绝、插话、打断或要求收束；待处理的发言或收束请求可以取消并恢复自动推进。
- 世界运行台可以提供高级手工操作，但不能把底层调度职责全部转嫁给玩家。
- 故事书缺省的自动讨论上限是 4 轮；已有故事书显式保存的值归玩家所有，不因缺省值变化而被静默覆盖。
- `【旁观推进】` 发起的讨论在旁白总结并关闭后即完成当前玩家请求；Host 不应再强制建立新 Brief 或追加无关剧情拍。

### 5.6 界面与测试故事

- 深色茄紫主题和米白浅色主题都应保留。
- 前端优化不能以删除已有入口、隐藏功能或只保留开发控制台为代价。
- 《月影账簿》是后续开发与用户自测的默认故事书。
- 《月影账簿》的新故事保持空大纲，由导演在首次运行时创建。

## 7. 一项功能何时才算存在

角色扮演功能必须沿以下链路核对。

```text
产品语义
  → 领域数据与状态变更
  → API 或命令
  → 持久化与重新加载
  → Director / Actor 实际模型上下文或运行时编排
  → 玩家可发现的界面与反馈
```

只有 UI：可能是没有后端效果的空壳。只有 API：可能没有产品入口。只有字段：可能从未被运行时读取。只有提示词：可能没有后端强制约束。只有测试夹具：可能没有生产路径。只有其中一层时，状态必须写为“未核验”，不能写成“已实现”。

## 8. 本轮开发暴露出的工作方法问题

### 8.1 局部阅读被误当成完整调研

最初只读取了部分重点文件和检索结果，没有完整追踪 MVP 的提示词编辑、自动讨论、故事配置和持久化流程，却直接开始大范围实现。这导致已经存在的用户能力被遗漏，并使后续文档建立在不完整事实之上。

### 8.2 当前上下文压过历史产品事实

实现过程过度依赖当前对话和当前工作区最显眼的代码，把新增加的领域能力当成全部产品范围。后续修改必须同时核对历史 MVP、Git 基线、当前工作区和用户明确要求，不能让最近一次上下文覆盖更早的产品事实。

### 8.3 把底层原语误判为完整产品功能

世界、记忆、讨论和上下文配方拥有字段与操作接口，不代表玩家已经获得正确体验。把群组讨论的手工启动表单放在主要界面，就是把运行时调度原语直接暴露给玩家，却没有说明自动编排与玩家干预的关系。

### 8.4 UI/UX Skill 使用顺序错误

UI UX Pro Max Skill 只适合在产品语义和数据链路明确后辅助入口、层级、可访问性和视觉实现。它不能替代领域模型、API、持久化、Director/Actor 上下文和自动编排审查。本轮曾过早把问题描述为 UI 修复，因而少考虑后端和运行时；问题来自使用顺序和判断失误，不来自 Skill 本身。

### 8.5 文档缺少历史对照

[角色扮演功能现状清单](roleplay-feature-status.zh.md)记录了大量当前代码，但没有先完整对照 MVP，因此遗漏了提示词编辑和自动讨论等历史能力。后续更新状态时必须写明证据来自哪一层，并先核对是否为旧功能的恢复或优化。

### 8.6 大范围未提交改动增加了误伤风险

当前工作区包含大量跨领域、API、Client、文档和 fixture 的改动。后续 Agent 必须先读 diff，再修改目标文件；不得使用会覆盖工作区的还原、重置或批量替换操作。

## 9. 后续开发规范

### 9.1 先识别功能性质

每次修改前先判断它属于：恢复 MVP 已有能力、修复当前回退、完善已有主路径、真正新增能力，还是裁剪 Harness。不同性质不能混在同一结论中。

### 9.2 先画数据流，再改界面

涉及提示词、角色、讨论、记忆、世界状态或导演编排时，先写清数据所有者、更新入口、持久化位置、模型消费者和 UI 消费者，再开始实现界面。UI Skill 只能在这一步之后使用。

### 9.3 自动能力与手工干预并存

自动讨论、导演推进和角色调度应有正常自动路径；运行台提供观察、恢复和高级干预。优化自动化不等于删除手工能力，保留手工能力也不等于要求玩家承担调度。

### 9.4 裁剪必须从产品依赖反推

判断 Harness 功能是否应删除时，先检查 Storyweaver profile、领域服务、模型工具、浏览器 API 和 UI 是否依赖它。没有当前消费者且不承担未来已确认产品职责的能力，才进入裁剪候选清单。

### 9.5 文档不得超前宣称

文档只能陈述已经沿完整链路核对的行为。正在实现、只有局部源码或尚未进行用户自测的功能必须明确说明，不得用“已有入口”替代“可用”。用户负责产品自测，Agent 的代码检查不能代替用户确认。

## 10. 当前实现状态

Director 与 Actor 的模型请求使用有日志依据的请求历史投影：完整 Session 继续服务 UI、重写、审计与回放，模型历史只保留当前唤醒事务中的玩家输入、推理、工具调用、结果和纠正。上一轮已经结束的 reasoning、工具错误和正文不会重新进入后续请求；连续性来自有界 World、Plot Ledger、最新 Brief、讨论、Actor 主观感知与已批准记忆。具体机制和边界见[请求历史投影 Agent Note](../.agents/notes/implemented/architecture/2026-09-02-request-history-projection.zh.md)。

同会话重编现在同时保留可查看的旧输入/回答版本，并通过 Storyweaver 回合前检查点恢复 Story 权威运行态与 Actor 私有表层。检查点每个 Story 缺省保留 128 条且可由部署配置；超出保留窗口的非首回合重编会在 replacement 接纳前失败。当前对话轮数只在 `turn/end` 时增加，步骤数仍在每个 `step/end` 实时更新，因此模型完成前后不会出现轮数看似不变的误导。

群组讨论会先收集参与者私有立场，再自动推进公开发言权；单次公开席位允许 `speak`、显式沉默 `pass` 或满足严格语义的整场 `conclude`。总公开发言预算仍是 `maxRounds × participantIds.length`，但故事书缺省值及《月影账簿》仓库 fixture 已设为 4。缺省值只在字段缺失时物化，不迁移已有显式配置；本机存在多份历史《月影账簿》运行，后续排查必须先确认工作台当前选中的 StoryId，不能凭标题或任意一份 `story.json` 判断设置。

普通推进、活跃讨论调度与讨论总结使用彼此独立的有界纠偏计数，因此较早遗漏不会耗尽后续阶段。已具备 Brief 与旁白的活跃讨论若在调度前停止，Host 只要求调用 `director_dispatch_actors`；若讨论被过早开启，则同一条分阶段续步只补齐缺失前置条件，不重建 Outline、场景或讨论。进入 `summarizing` 后，Host 携带准确 World 与讨论修订，要求 Director 先以旁白总结再完成关闭。成功关闭即完成当前 `【旁观推进】` 请求，不追加新 Brief 或无关剧情拍。

当前回归覆盖会故意让 Director 在讨论开始后连续两次只返回普通文本，随后验证专用续步仍能完成讨论调度、携带准确修订进行总结，并在关闭后结束玩家回合；它还验证失败的调度不会被误算成完成推进。定向测试与 TypeScript 检查证明领域和编排路径，不代替真实模型产品验收。用户仍需在最新服务上验证开局工具调用数、讨论选择是否克制，以及缓存命中表现。

本地 `master` 包含尚未同步至 `origin/master` 的连续开发提交。`.tmp-empty-storybook-e2e-20260831-0159/`、`.tmp-service-logs/` 与 `.tmp/` 是未跟踪临时目录，不属于产品提交；后续 Agent 不得为了获得“干净工作树”而重置、删除或提交这些目录。运行服务使用源码启动，进程号和访问 token 会随重启变化，必须从当前监听进程和启动日志重新确认。
